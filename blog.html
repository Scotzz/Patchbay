12 ноября 2026 Дмитрий Краснов · Staff DBA PostgreSQL

Почему миграция с ADD COLUMN ... DEFAULT всё ещё может остановить прод

Начиная с PostgreSQL 11 добавление столбца с константным значением по умолчанию больше не переписывает таблицу целиком. Но проблема никуда не ушла — изменился её механизм: теперь узким местом становится очередь ожиданий на ACCESS EXCLUSIVE lock.

Если перед таблицей крутится долгий аналитический SELECT на 40 секунд, ваш быстрый ALTER TABLE встанет в очередь за ним, а все новые запросы записи и чтения встанут уже за ALTER TABLE. В итоге пул соединений исчерпывается за секунды.

Надёжный паттерн — явно ограничивать время ожидания блокировки через SET LOCAL lock_timeout = '1500ms' и повторять миграцию с паузой, а не оставлять её висеть в очереди бесконечно.

28 октября 2026 Мария Тарасова · Lead SRE Kubernetes

Ловим утечку памяти в Go-сервисах до того, как сработает OOMKiller в Kubernetes

Когда контейнер падает с OOMKilled (Exit 137), стандартный kubectl logs --previous чаще всего показывает обрыв строки без контекста. Чтобы не гадать по графикам RSS, достаточно снимать heap-профиль по порогу cgroup.

В Go 1.19+ параметр GOMEMLIMIT позволяет задать мягкий предел на уровне 80–85% от лимита контейнера. В паре с периодическим дампом /debug/pprof/heap при превышении 75% RSS вы получаете точный стек аллокаций ещё до убийства процесса ядром.

14 октября 2026 Анна Белова · Senior Frontend / Node Backend

Три таймаута в HTTP-клиенте, которые постоянно путают при интеграции внешних API

Единый параметр timeout: 5000 в библиотеках часто закрывает только ожидание заголовков ответа или, наоборот, только установку TCP-соединения. При деградации внешнего шлюза это приводит к зависшим воркерам.

Разделяйте три границы: connect timeout (обычно 300–800 мс), время до первого байта ответа (TTFB) и общий deadline на чтение тела ответа через AbortSignal.timeout. Если шлюз отдаёт поток медленно по одному байту, TTFB не спасёт — сработает только общий deadline на запрос.

02 октября 2026 Илья Воронин · Co-founder Процессы

Почему командные вики умирают через полгода и как помогает GitOps для runbook-ов

Главная причина протухания инструкций в корпоративной вики — разрыв между местом, где меняется код, и местом, где описано, как его чинить. После рефакторинга флагов или переименования сервиса никто не идёт править страницу в браузере.

Когда сниппет или runbook лежит рядом с сервисом в Git и попадает в поиск через PR-ревью, правило простое: обновил конфиг сервиса — обновил соседний файл в том же пул-реквесте. Версия среды и дата проверки обновляются автоматически.
